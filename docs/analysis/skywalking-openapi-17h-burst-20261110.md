# open-api `POST:/customers/{encryptPhone}` 17:00 之后请求情况分析

> 分析对象：`prod::open-api` → `POST:/customers/{encryptPhone}`
> 时间范围：2026-11-10 17:00 ~ 17:21（+08）= 09:00 ~ 09:21 UTC
> 数据来源：SkyWalking（服务端时区 UTC，报告统一换算为 +08）
> 服务实例：`open-api-56ccb6b589-fjgx2`（**仅此 1 个实例**）

## 一、结论摘要

1. **17:00 之后共出现 3 波压测级突发**，合计 ≥216 条请求，而当天此前每分钟只有 1~2 条。
2. **只有 09:16:04 UTC（17:16:04 +08）的 16 条产生 error**，耗时集中在 **10.28~10.44 秒**，全部 HTTP 500。
3. **断点不是某个服务宕机，而是超时级联**：
   `lms-backend → risk-open-api` 的 HTTP 调用以 **10009ms 超时（status=-1）** 放弃，
   而 risk-open-api 实际跑了 **12203ms 后仍然成功**（status=200）。
4. **risk 慢的根因是 MySQL 连接池（HikariCP）被打满**：
   `HikariCP/Connection/getConnection` 单次耗时 **4089ms**（正常 0~4ms，慢约 1000 倍）。
5. **后两波（17:16:50、17:20:53）没有报错**，因为耗时虽被放大到 1.8~5.4 秒，但**没有突破 10 秒超时线**。
6. **业务隐患**：超时的 16 条请求，risk 侧数据实际已完整落库（客户创建、定价、授信申请），
   **存在重复写入风险**。

### 3.1 批次特征

| 项 | 值 |

### 3.2 断点位置

```
open-api  Exit /lms/quota/credit          10370ms   status=200
  └─ lms  Entry POST:/quota/credit        10343ms   status=200  [ERROR]
       └─ lms  Exit /api/v1/de/execute    10009ms   status=-1   [ERROR]  ← 断在这里
            └─ risk  Entry POST:/execute  12203ms   status=200  ← 实际成功了
```

**关键证据：**

| Span | 耗时 | 状态 | 含义 |
|---|---|---|---|
| `lms → risk /api/v1/de/execute` | **10009ms** | **status=-1** | **客户端超时放弃**（status=-1 = 连接中断/超时，非 HTTP 码） |
| `risk Entry POST:/execute` | **12203ms** | status=200 | **服务端实际跑完并成功** |

**risk 比 lms 的超时线多花了 2.2 秒**，结果回来时调用方已经放弃。

### 3.6 根因链条

```
17:16:04 同一秒 16 个请求涌入（单实例）
        ↓
risk-open-api 的 MySQL 连接池（HikariCP）瞬时打满
        ↓
后续请求排队取连接，最长等待 4089ms
        ↓
等待期间连接 / CPU 全线争抢，所有节点与 SQL 耗时放大 8~93 倍
        ↓
单请求总耗时被拉到 12.2 秒
        ↓
lms 的 HTTP 客户端超时阈值 = 10 秒（实测 10009ms）
        ↓
lms 先放弃 → 返回 200 + 残缺 body
        ↓
open-api 组装失败 → HTTP 500
        ↓
（risk 仍在继续，2.2 秒后成功提交，数据已落库）
```

### 3.7 ⚠️ 业务隐患：数据已落库，调用方认为失败

该请求在 risk 侧完整写入了以下数据（`status=200`）：

```sql
INSERT INTO b_customer              -- 新客户创建
INSERT INTO b_customer_history_2
INSERT INTO b_risk_pricing_2        -- 风控定价
INSERT INTO b_credit_apply_2        -- 授信申请（含 reject_type / reason）
INSERT INTO b_customer_quota_history_2
INSERT INTO b_customer_quota_flow_2
```

而 open-api 对外返回 **500**。后果：

- 上游/客户端认为是失败
- 若重试 → **重复创建客户、重复生成定价、重复授信申请**
- 这 16 条并发请求，可能已产生 16 份重复数据

**这是比 500 本身更严重的风险：超时路径没有幂等保护。**

## 五、容量拐点

以「MTN 停用 + 全量策略」这条路径为基准：

| 负载状态 | 耗时 | 相对空载 |
|---|---|---|
| 空载（1 请求/10s） | **600~900ms** | 1.0× |
| ≈10 QPS（批次 C） | **1835~3664ms** | 3~5× |
| ≈10 QPS（批次 B） | **4101~5371ms** | 6~8× |
| ≈16 QPS（批次 A） | **10286~10438ms** | **15~17×** |

**结论：单实例在此链路上的稳定容量远低于 10 QPS。**
大约在 **10 QPS 时 P50 开始进入 3~5 秒区间**，超过阈值后呈非线性劣化。

## 六、问题清单（按优先级）

| 优先级 | 问题 | 证据 | 影响 |
|---|---|---|---|
| **P0** | **risk-open-api HikariCP 连接池不足** | `getConnection` 4089ms（正常 0~4ms） | 直接导致 10 秒超时与 500 |
| **P0** | **超时路径缺幂等** | risk 已落库 6 张表，但对外返回 500 | 重试会产生重复客户/重复授信 |
| **P0** | **lms → risk 超时阈值 10s 不合理** | 超时 10009ms，risk 实际 12203ms | 等 10 秒仍然失败，纯浪费 |
| **P1** | **open-api / risk-open-api 均单实例** | 实例列表 count=1 | 16 并发即打满，无横向扩展能力 |
| **P1** | **风控配置表无缓存** | `t_risk_rule` 93ms/次，每请求查 5 次 | 压测时被放大 93 倍 |
| **P1** | **MongoDB 写入排队** | `MixedBulkWrite` 单次 80~118ms（正常 5~10ms） | 压测中占总耗时 30%+ |
| **P2** | **收尾单行 SQL 未 batch** | 20+ 条独立 `execute`，最长 93ms | 叠加放大 |
| **P2** | **`activiti connection adder` 出现** | 194ms | Activiti 自己的连接池也在扩容 |

## 七、建议

### 7.1 立即处理（P0）

1. **扩容 risk-open-api 的 HikariCP 连接池**
   - 同时排查是否存在连接未归还/泄漏（`connection adder` 反复出现是信号）
   - 目标：`getConnection` 稳定在 10ms 以内

2. **补幂等保护**
   - risk 侧按 `trace_id` 或业务唯一键做写入去重
   - 或改为「先占位再落库」，避免超时后重复写入

3. **调整 lms → risk 超时与降级**
   - 现状：等 10 秒 + risk 跑 12 秒 = 必然失败
   - 建议：超时压到 3~5 秒，超时后走「降级结果 + 异步补偿」，而不是让上游干等

### 7.2 短期优化（P1）

4. **open-api / risk-open-api 横向扩容**（至少 2~3 副本），并确认负载均衡生效
5. **风控配置元数据（规则 / 决策表 / 规则集 / 模型）加本地缓存**
6. **MongoDB 写入优化**：合并多次写、检查副本集写入延迟与连接池

### 7.3 中期优化（P2）

7. **收尾 20+ 条单行 SQL 改 `executeBatch`**
8. **Doris 特征表列裁剪 + 同表合并查询**
9. **MTN 恢复调用前**，先完成 `flags/history` 并行化与 usage 结果缓存
   （参考：MTN 正常时该链路会额外增加 800~2000ms）
