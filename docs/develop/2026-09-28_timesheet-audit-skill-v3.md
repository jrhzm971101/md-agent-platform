description: 月度工时填报核对流程。当用户提出核对某月工时填报情况、找出未填或少填工时的员工、或要求按月审计工时数据时使用。规定花名册怎么取、怎么按 10 人分片并发核对、取数纪律（按 userid 精确取数、禁止整表拉取）、核对口径（应填工作日与 8h 阈值）、结果怎么汇总输出，以及如何征询并按用户确认下发提醒。
---
## 适用场景

用户要求核对某个时间范围内员工的工时填报情况：哪些工作日没填、哪些填得不足 8h、哪些必填字段空着，
并（在用户确认后）把提醒下发到人。

## 触发与参数

用户提出核对工时类诉求时进入本流程。先按下表取参数，**任何一项拿不到就先向调用方确认，不要用默认值猜**。

| 参数 | 默认 | 说明 |
| --- | --- | --- |
| 时间范围 | 必填 | 核对哪个月，如 `2026-09`；用户只说"上个月"就换算成具体月份并复述确认 |
| 花名册来源 | `在职花名册`（智能文档） | 提供全员名单与 userid |
| 工时来源 | `MD-timesheet-new`（智能表格） | 提供每个人逐日的工时记录 |
| 分片大小 | 10 | 每个子 agent 负责的人员数 |
| 并发上限 | 10 | 同时活跃的子 agent 数 |
| 工时阈值 | 8h | 每个工作日的最低工时 |
| 结果落盘 | `audit-results/<时间范围>-timesheet.md` | 报告在工作区留痕的路径 |

> 「分片大小」「并发上限」全流程只有这一处定义。第 5 步报告里的同名数字必须与这里一致 ——
> 这两处曾各写各的（表格写 10、报告写 5），对账时没人能判断哪个是真的。

## 已核实的资源定位（2026-09-28 实测，可直接使用）

| 用途 | 文档 | docid | 子表 | sheet_id |
| --- | --- | --- | --- | --- |
| 花名册 | 在职花名册（约 87 人） | `s3_ARQAVQZTAEcCNNb5ScWL9RbiVhy7o` | 员工数据 | `q5Fkjm` |
| 工时 | MD-timesheet-new（4498 条 / 28 列） | `s3_AJsAOQacAHECN6z6WqmxAQNirj5y1` | 工时填报 | `q979lj` |

- 花名册列（4 个）：`姓名`(text)、`姓名(人员)`(user)、`别名`(text)、`一级部门`(single_select)
- 工时表关键列：`姓名`(user，field_id `fSNPFZ`)、`日期`(date_time)、`工时(必填)`(number)，
  另需 `任务需求(必填)`、`投入目的(必填)`、`任务主体(必填)`
- **对齐键是 user 类型列里的 userId**：花名册取 `姓名(人员)`，工时表取 `姓名`。
  文本 `姓名` / `别名` 只用于展示和复核，**不要拿来对齐**（同名、改名、中英文混排都会错）。
- ⚠️ 工时表 `forbid_sql_query=true`：**不要**尝试用 `smartsheet_records_query_submit` 走 SQL 取数，只能过滤 + 分页读。
- ⚠️ 用 `doc_search` 搜「在职花名册」会**同时命中一个同名普通 sheet**（`在职花名册 26-09-03_135511(1)`）。
  必须带 `doc_types:["smartsheet"]`，或直接按上表 docid 取。
- 上表是「已知值」不是「唯一真相」：若实测 docid / sheet_id 与表里不符，说明文档被重建过 ——
  按实测值继续，并把差异写进报告的「未覆盖与失败」一节，**不要静默换用**。

## 核对口径（开跑前固定，不要边跑边改）

- **应填日**：该时间范围内的工作日，一律由 `workday-query`（`scope=month`）判定并取 `workdays` 列表。
  禁止按"周一到周五"或"周末休息"推断——调休补班与法定假日都会让星期推断出错，且模型无法自行发现。
- **关联键**：user 类型列里的 `userId`（见上节）。**不要用文本姓名**。
- **逐人逐日核对**，异常分三类，不要混成一句"填报有问题"：

| 异常类型 | 判定 |
| --- | --- |
| 未填报 | 该工作日应填，但工时表里没有这个人的当天记录 |
| 工时不足 | 有记录，但当天工时 < 工时阈值（默认 8h） |
| 必填字段缺失 | 除「备注」外的必填列有空值 |

- **提示项（不计入异常）**：在非工作日填了工时，单独列为"非工作日填报"，供调用方判断。
- 汇总口径固定为：应核对人数 / 实际覆盖人数 / 正常人数 / 异常人数（按三类拆分）/ 未覆盖人数。

## 取数纪律（成本红线，逐条执行）

这一节不是"优化建议"，是硬约束。整表拉取是本流程唯一能把成本放大十倍的动作。

1. **按人取数，不按表取数。** 抓整表后，原始记录会留在上下文里，之后**每一轮都会重发一次**：
   实测一个分片 9 轮吃掉 9.4M 输入 token，是同规模精确取数的十几倍。
   `smartsheet_records_list` 必须带 `filter_spec`，把范围收窄到「本片人员 + 本时间范围」。
2. **只取需要的列。** 用 `field_titles` 白名单只列核对真正要用的列（日期、工时、必填文本列）。
   28 列 × 4498 行 与 5 列 × 本片行数，不是一个量级。
3. **先验证条件真的生效。** 只给一个 userId 时，返回行数应当是个位数到几十。
   若行数量级等于全表（数千），说明过滤没生效（`operator` 或取值字段放错），
   **立刻停手**改条件，**不要把整表结果继续带进后续轮次**。
4. **单次 `limit` 不超过 1000**，`start` 上限 100000；超过一页才翻页，且只翻本片需要的页。
5. **同一范围只取一次。** 取回来当轮就折算成"每人一行"的结论；后续轮次只带结论，不再重复携带原始记录。
6. **不要重复探查结构。** 文档 / 子表 / 列名已由父侧钉死在指令里，分片**不许**再 `doc_search`，
   也不许反复 `smartsheet_fields_list` 试探——那是每片一次的网络往返 + 一份常驻上下文。
   只有指令里明确写了"此项未知，需要你自己查"时才去查。

### 按人取一条（实测可用形状）

```json
{
  "docid": "s3_AJsAOQacAHECN6z6WqmxAQNirj5y1",
  "sheet_id": "q979lj",
  "type": "records",
  "field_titles": ["日期", "工时(必填)", "任务需求(必填)", "投入目的(必填)", "任务主体(必填)"],
  "filter_spec": {
    "conjunction": "and",
    "conditions": [
      { "field_id": "fSNPFZ", "field_type": "user", "operator": "is", "user_value": { "value": ["<userId>"] } }
    ]
  },
  "limit": 100
}
```

- 取值必须放在与该列类型匹配的字段下：user 列用 `user_value.value[]`、number 列用 `number_value.value`、
  文本列用 `string_value.value[]`、日期列用 `date_time_value.value[]`。
- user 列实测 operator 用 `is`；number 列实测 `eq` 可用。
- 第一次只给一个 `user_value`，是为了让"条件是否生效"可验证（见纪律 3）；
  确认生效后可按小批（≤10 个 userId）合并条件，但**不要**一次把全片几十人塞进去。

## 流程

### 第 1 步 取花名册 + 固化取数上下文（父侧自己做，不下发给分片）

1. `doc_search`：`{"keywords":["在职花名册"],"doc_types":["smartsheet"],"search_scope":"title","limit":20}`；
   已确认过就直接用上节的 docid，省掉这一步
2. `smartsheet_get` / `smartsheet_sheets_list`（`docid` 必填）定位数据子表「员工数据」与 `sheet_id`
3. `smartsheet_fields_list`（`docid` + `sheet_id`）**读一次**字段定义，确认哪个 user 列是人员标识
4. `smartsheet_records_list` 读全员（实测形状：`{"docid":"...","sheet_id":"q5Fkjm","type":"records","key_type":"field_title","limit":200}`），
   整理成 `[{name, userId}]`
5. 产出一份**公共取数上下文**，它就是下发给每个分片的原件：
   - 花名册：docid / sheet_id / 人员列名
   - 工时表：docid / sheet_id / 人员列（title + field_id）/ 日期列 / 工时列 / 必填列清单
   - 时间范围、工时阈值、三类异常口径
   - 本片人员 `[{name, userId}]`

花名册里找不到 user 类型列时**停下来问调用方**是哪一列，不要用文本姓名或工号顶替，也不要自己编。

### 第 2 步 分片

- 按分片大小切成若干片：片与片之间**不重叠、不遗漏**
- 每片记录：分片序号、本片 `[{name, userId}]`、时间范围
- 分片清单要留痕（报告里要写清楚"哪些人被处理过"）

### 第 3 步 并发派发子 agent

- 每片派给 **`workwx_doc_agent`**（它同时具备企微文档 MCP 与 `workday-query`）
- 同时活跃的分片数不超过并发上限，其余分批排队，一批结束再起下一批
- **每片指令必须自带全部输入**，子 agent 是独立会话，看不到你的上下文。指令内容 = 第 1 步的
  「公共取数上下文」**原样附上**，再加下面三项：
  - 本片人员清单（姓名 + userId，一个不漏）
  - **「取数纪律」全文附上**（纪律 1~6）——这是成本与正确性的分水岭，别只丢一句"注意别读全表"
  - 期望输出：一份 markdown 明细表，列 = 姓名 / userId / 应填天数 / 实填天数 / 异常类型 / 具体日期与差异
- **工作日日期列表不写进指令**：只给月份，让分片自己调 `workday-query`（该查询在进程内按年缓存，各分片分别调用不会重复请求外部）。把日期列表用自然语言转述给分片，很容易漏项或概括，而分片无法发现被改错。
- **要求分片只回文本结论、不要写文件**：本 agent 与子 agent 共享同一工作区，多个分片同时写同一文件会互相覆盖。结果的唯一汇总点在父侧。
- **派发方式**：默认后台 —— `timeout_seconds=0` 拿到 `task_id` 后用 `wait_async_results(wait_all=true)` 等齐；
  被 promote 的任务继续等，**不要重发同一个任务**。
  若这次派发**直接同步返回了结果、没有 `task_id`**（编排把子 agent 配成了强制同步），
  就直接用返回值，不要去找 `task_id`、也不要重发。

### 第 4 步 等待与汇总（父侧）

- 必须等到该批全部任务进入终态再汇总，不要凭"应该跑完了"提前总结
- 合并各片结果、跨片去重、统一异常分类
- 自己复核一遍总数：应核对 N 人 = 覆盖 M 人 + 未覆盖 K 人；对不上就说明分片漏发或结果丢失，要回头查，不要直接把数字写进报告
- 子 agent 报错的片：记录失败范围与原因，能重试的换片重试，不能重试的记为**未覆盖项**

### 第 5 步 输出报告

按下面结构输出 markdown（同时写入结果落盘路径）：

```markdown
# {时间范围} 月度工时核对报告

- 核对范围：{起} ~ {止}，共 {N} 个工作日（来源：workday-query）
- 花名册：{花名册名}，共 {X} 人
- 工时来源：{工时表名}
- 判定口径：每个工作日工时 ≥ {阈值}h；除「备注」外必填列不允许为空
- 结论：正常 {a} 人 · 异常 {b} 人（未填报 {b1} / 工时不足 {b2} / 字段缺失 {b3}）

## 异常明细

| 姓名 | userid | 应填天数 | 实填天数 | 异常类型 | 具体日期与差异 |
| --- | --- | --- | --- | --- | --- |
| ... |

## 非工作日填报（提示项）

| 姓名 | userid | 日期 | 工时 |
| --- | --- | --- | --- |

## 未覆盖与失败

| 姓名/分片 | 原因 |
| --- | --- |

## 分片与并发说明

- 分片大小 {10}，并发上限 {10}，共 {k} 片
- 取数方式：按 userId 精确过滤（`filter_spec`），未做整表拉取
```

报告的最后一行「取数方式」是留给事后核查的：它让"这次跑得贵不贵"能在报告里被看见，
而不是只能靠翻调用日志才发现某个分片又把整表拉了一遍。

## 何时提醒用户（可选的收尾）

核对完成后**先问用户是否要下发提醒**，不要自动群发。用户确认后：
- 逐人或按部门下发，不要把全员异常明细一次性群发
- 下发后确认推送状态（成功 / 失败名单），失败的记为未覆盖项
- 最终把"核对结果 + 推送结果"合并成一份完整汇报返回给用户

> 离线批量任务建议放到非工作高峰时段跑：同样的 token 量在闲时约省一半费用。
